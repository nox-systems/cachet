## 1. How respected self-hosted projects stage config and secrets

**The dominant pattern: `.env` file sitting next to the compose/stack definition, inside the checkout, gitignored.** Every one of the surveyed Docker-world projects does this. The outliers that keep config *outside* the checkout are MinIO (`/etc`) and n8n (`~/.n8n`).

- **PocketBase** — single binary; config is flags + env vars; a 32-char `PB_ENCRYPTION_KEY` env var referenced by `--encryptionEnv` encrypts settings that otherwise sit as plain JSON in the SQLite DB. Deployment is rsync of one directory; recovery = restore `pb_data/` (manual copy, or built-in ZIP backups to local/S3). Docs: https://pocketbase.io/docs/going-to-production/
- **Umami** — `.env` with `DATABASE_URL` + `APP_SECRET` (`openssl rand -hex 32`); upgrade is `git pull &amp;&amp; pnpm install &amp;&amp; pnpm build` or `docker pull &amp;&amp; docker compose up -d`. State lives in Postgres, so losing the `.env` costs only the APP_SECRET (invalidates tokens). Docs: https://umami.is/docs/environment-variables, https://umami.is/docs/install, https://docs.umami.is/docs/updates
- **Supabase self-hosting** — clone the repo, copy `docker/.env.example` to `docker/.env`, run `utils/generate-keys.sh` + `utils/add-new-auth-keys.sh` to fill secrets. `update.sh` does a three-way merge over your files on upgrade (your `.env` survives by virtue of the merge; `reset.sh` backs it up to `.env.old`). Docs explicitly say "all secrets are in the `.env` file by default; we strongly recommend using a secrets manager in production" (Doppler, Infisical, Vault, cloud secret managers). Losing the `.env` = losing the JWT secret lineage; keys must be regenerated. Docs: https://supabase.com/docs/guides/self-hosting/docker, env reference: https://github.com/supabase/supabase/blob/master/docker/CONFIG.md
- **Infisical (self-hosted)** — same shape: `.env` with `ENCRYPTION_KEY` (16-byte hex), `AUTH_SECRET` (32-byte base64), `DB_CONNECTION_URI`, `REDIS_URL`. Docs give the exact `openssl rand` commands they expect operators to paste. https://infisical.com/docs/self-hosting/configuration/envars
- **Documenso** — `cp .env.example .env`; docs ship a required-var table (`NEXTAUTH_SECRET`, two encryption keys, DB URL, SMTP). https://docs.documenso.com/docs/self-hosting/configuration/environment, https://docs.documenso.com/docs/self-hosting/deployment/manual
- **MinIO** — the strongest "config outside the checkout" example: systemd unit loads `EnvironmentFile=/etc/default/minio`, which only points at the real config file `/etc/minio/config.env` via `MINIO_CONFIG_ENV_FILE`; upgrade is a package replacement that never touches `/etc`. https://github.com/minio/minio-service/blob/master/linux-systemd/README.md, https://github.com/minio/minio-service/blob/master/linux-systemd/minio.service
- **n8n** — home-dir custody: first launch generates a credential-encryption key into `~/.n8n/config`; env var `N8N_ENCRYPTION_KEY` (and a `_FILE` suffix variant) override only if the file doesn't already hold a key. Losing that file means stored credentials are unrecoverable — the community thread confirms changing the supply mechanism post-hoc resets the instance. https://docs.n8n.io/deploy/host-n8n/configure-n8n/basic-configuration/configuration-examples/set-a-custom-encryption-key, https://community.n8n.io/t/274522
- **Tailscale operator** — placeholders in `deploy/manifests/operator.yaml` (`client_id`/`client_secret` go into a K8s Secret `operator-oauth`); Helm values create the Secret for you. tsnet device state itself is stored in a Secret. https://tailscale.com/docs/kubernetes-operator/install-operator, https://github.com/tailscale/tailscale/blob/main/cmd/k8s-operator/deploy/manifests/operator.yaml

**Common thread for recovery:** the state store (Postgres, `pb_data`, Cloudflare account resources) survives config loss; what dies is minted secrets, which every project treats as re-issuable by rerunning the generation step. None of them treat the clone as precious — but their `.env` *does* live in the clone, so "disposable clone" is only half-achieved by the mainstream pattern.

## 2. The "config outside the clone" pattern — tool status, 2026

- **XDG / home-dir custody** is the CLI-world standard (see §4) and the server-world precedent is MinIO's `/etc`. Nobody in the Docker cohort bothers because the compose file pins them to a directory.
- **dotenvx** — active and credible. secp256k1; encrypted `.env` is commit-safe, `.env.keys` is the uncommitted crown jewel; CI injects `DOTENV_PRIVATE_KEY=... dotenvx run -- cmd`; documents 1Password/Bitwarden sourcing (`$(op read ...)`) for the private key. Newer `dotenvx armor up` stores keys off-device. https://dotenvx.com/docs/env-keys-file, https://dotenvx.com/docs/cli/encrypt-fk
- **sops + age** — CNCF Sandbox (healthy, growing contributors); age is the recommended backend; `sops exec-env` injects decrypted env into a command — a clean fit for "optional vault" glue. https://www.cncf.io/projects/sops/, https://getsops.io/
- **ejson (Shopify)** — **not archived** (search results claiming otherwise are stale); last release v1.5.4 Feb 2025, commits into 2026. Viable but a smaller ecosystem than sops/dotenvx. https://github.com/Shopify/ejson
- **varlock** (2025-era, dmno-dev) — `.env.schema` with `@required @sensitive @type=string(...)` decorators, `varlock scan` leak detection; the most credible current answer to "env contract validation as code." https://varlock.dev/guides/schema/, https://varlock.dev/env-spec/overview/, https://github.com/dmno-dev/varlock
- For a one-worker deployment the right baseline is **plain dotenv-format file at 0600 in an XDG path** (zero tooling), with dotenvx/sops/op/infisical as opt-in sourcing layers — they all converge on "decrypt → export env → run command," so anything reading env vars supports all four for free.

## 3. Programmatic deployments (Pulumi-like / alchemy)

- **Pulumi:** `pulumi new` scaffolds from templates; per-stack `Pulumi.&lt;stack&gt;.yaml` is *committed to the consumer's repo* with secrets encrypted inline (`secretsprovider` + `encryptedkey` fields). Local/object-store backends default to the `passphrase` provider — no Pulumi Cloud required; `--secrets-provider` overrides to KMS/Vault. ESC exists for shared config but is Pulumi-Cloud-dependent. So Pulumi's answer to "custody" is: encrypted-in-your-repo, key elsewhere. https://www.pulumi.com/docs/iac/cli/commands/pulumi_new/, https://www.pulumi.com/docs/iac/concepts/secrets/, https://www.pulumi.com/docs/iac/concepts/projects/stack-settings-file/, https://www.pulumi.com/docs/esc/concepts/environments/
- **Alchemy (v2, what cachet uses):** secrets come from the **deployer's process environment** (conventionally a `.env` loaded by the operator); `Config.redacted("NAME")` binds as Cloudflare `secret_text` regardless of constructor. Local state lives in `.alchemy/` (gitignored, stack+stage-scoped JSON); secrets in state are encrypted with a password passed at init (e.g. `SECRET_PASSPHRASE`); losing the password or state doesn't lose the deployed resources since the names are deterministic. `alchemy create` scaffolds consumer projects from templates. **There is no alchemy-native custody convention beyond "env of whoever runs the deploy" — cachet must define it.** https://alchemy.run/concepts/secrets/, https://alchemy.run/concepts/state/, https://alchemy.run/concepts/secret, https://alchemy.run/concepts/cli

## 4. Secrets-entry UX convergence in good CLIs

All five converged on the same shape: **interactive auth → write 0600/keystore entry under a home/XDG path → env var is the CI override.**

- **gh:** OS keyring (macOS Keychain / Secret Service / wincred), fallback plaintext `~/.config/gh/hosts.yml`; `GH_TOKEN` for CI. https://cli.github.com/manual/gh_auth_login, https://github.com/cli/cli/pull/7023
- **wrangler:** `~/.config/.wrangler/config/default.toml` (XDG-aware, mode 0600); as of **June 2026**, opt-in `--use-keyring` stores an AES-256-GCM file with the key in the OS keychain; `CLOUDFLARE_API_TOKEN` is the CI path; `wrangler whoami` reports where credentials live. https://developers.cloudflare.com/workers/wrangler/commands/general/, https://developers.cloudflare.com/changelog/post/2026-06-03-wrangler-keyring-credential-storage/
- **flyctl:** `~/.fly/config.yml` `access_token:`; `FLY_ACCESS_TOKEN` wins (and gets persisted). https://github.com/superfly/flyctl/blob/master/internal/config/config.go
- **supabase CLI:** `~/.supabase/access-token` (newer versions keyring); `SUPABASE_ACCESS_TOKEN` is the documented CI mechanism. https://supabase.com/docs/reference/cli/introduction
- **stripe CLI:** `~/.config/stripe/config.toml`, and notably `stripe login` mints a **restricted key (`rk_…`)** — the stored credential is minimally-scoped by construction; `STRIPE_API_KEY` env override. https://docs.stripe.com/stripe-cli/keys, https://docs.stripe.com/cli/config

Two takeaways: XDG paths with 0600 are the uncontroversial baseline (nobody forces a password manager); scope-minimizing the stored credential (stripe) is the differentiator — cachet's bootstrap already demands a *scoped* Cloudflare API token list in DEPLOY.md, which is the right instinct.

## 5. Env-contract docs and token verification at bootstrap

- **Contract-as-docs:** Supabase's `docker/CONFIG.md` (aggregated var reference), Documenso's and Infisical's required-var tables with exact generation commands. Contract-as-code: varlock's `.env.schema`.
- **Verification endpoints that exist and are cheap:**
  - Cloudflare: `GET /client/v4/user/tokens/verify` returns `{id, status: active|disabled|expired, expires_on}` — the canonical bootstrap probe. https://developers.cloudflare.com/api/resources/user/subresources/tokens/methods/verify/
  - GitHub OAuth app: `POST /applications/{client_id}/token` (basic auth with client_id/client_secret) checks a token belongs to that app (404 if not). https://docs.github.com/en/rest/apps/oauth-applications
  - GitHub scopes surface in `X-OAuth-Scopes` response headers (how `gh auth status` shows them).
  - Note: a GitHub OAuth *client secret* cannot be verified without running an OAuth flow; bootstrap can only format-check it and verify the client_id.

## Recommended custody model for cachet

**1. Move the operator env file out of the clone.** Canonical location `${XDG_CONFIG_HOME:-~/.config}/cachet/deploy/&lt;stage&gt;.env`, mode 0600, written by `just bootstrap` instead of today's `infra/.env.production`. Precedence, matching every CLI surveyed: process env &gt; `$CACHET_DEPLOY_CONFIG` (explicit file path) &gt; XDG file &gt; in-clone `infra/.env.&lt;stage&gt;` with a deprecation warning. `just deploy`/`just destroy` source through that chain (today they only check `infra/.env.&lt;stage&gt;` — justfile lines 111–136). Clone deletion then destroys only code and alchemy local state; `infra/.alchemy` state loss is non-catastrophic because alchemy resource names are deterministic and re-converges, and the secrets themselves live in the XDG file and as Cloudflare bindings.

**2. Bootstrap prompts with verification, not blind prompts.** Current `scripts/bootstrap.sh` already collects and generates; extend it to (a) probe `CLOUDFLARE_API_TOKEN` against `/user/tokens/verify` and require `status: active` before writing the file, (b) format-check `CACHET_SIGNING_KEY` (`&lt;host&gt;-N:` + base64 of 32 bytes) against the printed matching public key, (c) length/format-check the OAuth client_id/secret (GitHub `Iv1.`/20-hex shapes) and state plainly that the secret is only proven at first real OAuth callback, (d) `chmod 0600` and print the file's path and the recovery note.

**3. Recovery is a re-issue runbook, mirroring the surveyed projects.** Losing the file loses three re-mintable things: signing key (`cachet keygen --name &lt;host&gt;-N`, already the documented rotation path), OAuth client secret (GitHub settings), Cloudflare token (dashboard). Document that `just bootstrap` can re-run against the same host and cross-check answers against the live deployment's `/api/public/config` (host, orgs, client id, current key prefix are all public there), so re-bootstrap is also the "I lost my config" path. Non-secret values are recoverable from the existing deployment's public surface.

**4. CI needs no fork and no file.** Keep the current DEPLOY.md model — GitHub environment secrets/vars exported into the job — since env-over-file precedence makes it identical mechanics to local. This matches the GH_TOKEN/CLOUDFLARE_API_TOKEN/SUPABASE_ACCESS_TOKEN convention exactly; operators using a different CI (or `pulumi`-style hosted state) map the same variable names.

**5. Optional vaults plug in through the env contract, never through cachet code.** Because values enter strictly as env vars: `op run --env-file=cachet.env -- just deploy production`, `infisical run -- just deploy production`, `dotenvx run -f ~/.config/cachet/deploy/.env.production.enc -- just deploy production`, or `sops exec-env secrets.env 'just deploy production'`. List these as one column in DEPLOY.md's variable table; install nothing. Stripe's lesson applies where possible: the bootstrap checklist should keep demanding the narrow Cloudflare token scope set rather than a global key.

**6. Keep the env contract in one committed example file plus a validator.** Commit `infra/.env.example` (mirroring Supabase/Infisical/Documenso's `.env.example` pattern) as the single source of the contract; `just bootstrap` is the validating writer. If a validator-in-repo is wanted, the varlock-style `.env.schema` is the credible 2026 option, but a 15-line shell check at bootstrap is sufficient for ~10 vars and avoids a dependency — cite the former in docs, ship the latter.

**7. Do not copy Pulumi's encrypted-in-repo default.** Committing encrypted config (pulumi passphrase model, dotenvx-encrypted `.env` in the clone) re-couples custody to the checkout and adds a key file to manage. The XDG-file-with-env-override model is simpler, matches gh/wrangler/stripe precedent, and leaves all four encryption tools usable by operators who want them.

# Operator-side CI/CD for OSS deployables on GitHub Actions (verified August 2026)

## 1. Reusable workflows (`workflow_call`) as the operator-facing deploy product

**Mechanics, verified against docs.github.com** ([Reuse workflows](https://docs.github.com/en/actions/how-tos/reuse-automations/reuse-workflows), [Workflow syntax](https://docs.github.com/actions/using-workflows/workflow-syntax-for-github-actions)):

- Caller references: `uses: {owner}/{repo}/.github/workflows/{file}@{ref}` — works cross-org for **public** repos. `{ref}` may be a tag, branch, or **full SHA**; docs: "Using the commit SHA is the safest option for stability and security." The workflow version executed is the one at that ref.
- Secrets are **never auto-passed** cross-boundary. The caller passes them explicitly (`secrets: { name: ${{ secrets.X }} }`) or with `secrets: inherit`. A caller passing an undeclared secret is an error. Documented quirk that matters for cachet: `secrets: inherit` is designed for same-org/same-enterprise calls and **fails at evaluation time for cross-org calls** even when the names exist ([diogenes-project/diogenes#221](https://github.com/diogenes-project/diogenes/issues/221), [actions/runner#3206](https://github.com/actions/runner/issues/3206), [github/docs#44458](https://github.com/github/docs/issues/44458)). Since operators live outside the nox-systems org, the upstream workflow must declare every secret by name and operators must map them explicitly.
- **Environment protection rules resolve against the caller repo.** The called workflow can't take `environment` at `on.workflow_call`, but its jobs can set `environment: ${{ inputs.stage }}` (expressions are allowed); required reviewers on the *operator's* "production" environment then gate the job, including secret access ([Deploying with environments](https://docs.github.com/en/actions/reference/workflows-and-actions/deployments-and-environments), [actions/runner#4453](https://github.com/actions/runner/issues/4453)). Caveat: environment-scoped secrets resolve inside the called workflow only when the caller also passes them (`secrets: inherit` being broken cross-org, operators must map env secrets explicitly by name).
- **Permissions flow down, never up**: "permissions can only be maintained or reduced" through the call chain. For OIDC, the *caller job* must grant `permissions: id-token: write`; a called workflow can't self-grant it ([changelog 2023-06-15](https://github.blog/changelog/2023-06-15-github-actions-securing-openid-connect-oidc-token-permissions-in-reusable-workflows/), [josh-ops guide](https://josh-ops.com/posts/github-actions-oidc-reusable-workflows/)). The tolerable side effect: **OIDC subject claims describe the caller repo and environment** (`repo:operator/repo:environment:production`), so cloud trust policies bound to the operator repo still hold even though the workflow code is upstream.
- Nesting max 10 levels, no loops; matrix can fan out calls; outputs return via `needs.&lt;job&gt;.outputs`.
- The called workflow's `GITHUB_TOKEN` is the **caller's repo token**; a public upstream repo can still be re-checked-out inside it at any ref via `actions/checkout` with `repository:`/`ref:`.

**Caller-side shape (pattern A, what cachet operators would write):**

```yaml
# operator repo: .github/workflows/cachet-deploy.yml
name: deploy cachet
on:
  workflow_dispatch:
    inputs:
      tag: { description: "cachet release tag", default: "v1.4.2" }
      stage: { description: "staging or production", default: "staging" }
  schedule: [ { cron: "17 4 * * 1" } ]   # weekly drift check, optional

jobs:
  deploy:
    permissions:
      contents: read          # job-level least privilege, nothing else needed
    uses: nox-systems/cachet/.github/workflows/operator-deploy.yml@v1.4.2
    with:
      stage: ${{ inputs.stage || 'staging' }}
      cachet-tag: ${{ inputs.tag || 'v1.4.2' }}
    secrets:
      CLOUDFLARE_API_TOKEN: ${{ secrets.CLOUDFLARE_API_TOKEN }}
      CLOUDFLARE_ACCOUNT_ID: ${{ secrets.CLOUDFLARE_ACCOUNT_ID }}
      CACHET_SIGNING_KEY: ${{ secrets.CACHET_SIGNING_KEY }}
      GITHUB_OAUTH_CLIENT_SECRET: ${{ secrets.GITHUB_OAUTH_CLIENT_SECRET }}
```

**Production examples doing this in the wild:**
- `slsa-framework/slsa-github-generator` — the marquee cross-org reusable workflow; its docs and open issues are the best existing study of tag-vs-SHA pinning friction ([issue #4216](https://github.com/slsa-framework/slsa-github-generator/issues/4216), [issue #4440](https://github.com/slsa-framework/slsa-github-generator/issues/4440): SHA-pinning callers broke their release-asset downloading and even violated GitHub's own "require SHA-pinned actions" org policy, because the workflow's *internal* `uses:` lines weren't SHA-pinned).
- [celo-org/reusable-workflows](https://github.com/celo-org/reusable-workflows) — versioned `@v3.0.0` tags, per-caller least-privilege `permissions:` blocks, optional `environment` input for deploy gating.
- [aws-samples/aws-terraform-reusable-workflow](https://github.com/aws-samples/aws-terraform-reusable-workflow/blob/main/.github/workflows/terraform-reusable.yml) — deploy/destroy as a callable product with `id-token: write` OIDC.
- [oslokommune/reusable-terraform-pr-plan](https://github.com/oslokommune/reusable-terraform-pr-plan) — municipal org running operator repos against a central workflow.
- The chrischall/setlist-mcp [deploy-at-release-tag pattern](https://github.com/chrischall/setlist-mcp/pull/70) shows the "deploy the released tag, not main" discipline.

## 2. Composite/JS action as the whole-deploy unit

Mechanics ([metadata syntax](https://docs.github.com/en/actions/reference/workflows-and-actions/metadata-syntax), [composite secrets](https://latchkey.dev/learn/github-actions/github-actions-composite-action-cannot-access-secrets), [nested uses](https://latchkey.dev/learn/github-actions/gha-composite-nested-uses-error)): a composite action **cannot read `secrets.*` at all** — the operator must pass every secret as a `with:` input, which is more verbose but forces the contract to be explicit. Composite steps may themselves `uses:` other actions. Local `./` paths inside it resolve against the action repo, so the action must be fully self-contained.

**Caller-side shape (pattern B):**

```yaml
jobs:
  deploy:
    runs-on: ubuntu-latest
    environment: production            # protection rules apply normally; job is the caller's own
    steps:
      - uses: nox-systems/cachet/deploy-action@v1
        with:
          stage: production
          cachet-tag: v1.4.2
        env:
          CLOUDFLARE_API_TOKEN: ${{ secrets.CLOUDFLARE_API_TOKEN }}
          CLOUDFLARE_ACCOUNT_ID: ${{ secrets.CLOUDFLARE_ACCOUNT_ID }}
          CACHET_SIGNING_KEY: ${{ secrets.CACHET_SIGNING_KEY }}
          GITHUB_OAUTH_CLIENT_SECRET: ${{ secrets.GITHUB_OAUTH_CLIENT_SECRET }}
```

Comparison to a reusable workflow as secret consumer: trust exposure is identical (upstream code runs with your secrets in both). The differences: an action keeps `environment:` on the operator's own job (reviewer gating is trivially unambiguous and env secret wiring has no inherit quirk), while a reusable workflow gives a full job graph, its own runner/OS choice, outputs, and isolates upstream's `permissions:` needs from the caller's jobs. The SLSA precedent suggests large security-conscious consumers prefer reusable workflows; every Cloudflare-adjacent OSS (cloudflare/wrangler-action, [BotCoder254/cloudflare-promoter](https://github.com/BotCoder254/cloudflare-promoter)) ships the action form. Note cachet already has precedent constraints: an action can't run `just`, so the deploy machinery must be invocable as `bun run deploy --stage X` (it already is — `infra/alchemy.run.ts`).

## 3. "No repo at all" options

- **Real answer: GitHub Actions always needs at least one repo** holding the caller workflow YAML. There is no scheduled/manual Actions run without a repo. The realistic floor is a tiny config repo with one workflow file, which doubles as the version-pin record (see §4).
- **Cloudflare Workers Builds** ([docs](https://developers.cloudflare.com/workers/ci-cd/builds/), [config](https://developers.cloudflare.com/workers/ci-cd/builds/configuration/)): connects a GitHub/GitLab repo the operator owns, builds on push to one **branch** (tags/releases not a trigger), deploy command is customizable but wrangler-shaped. Build image ([build-image docs](https://developers.cloudflare.com/workers/ci-cd/builds/build-image/)) is Ubuntu 24.04 with Node 22/24, Bun 1.2, Go, Python — **no Rust/cargo preinstalled**, and build variables/secrets are build-time only. For cachet that means building wasm in their CI container is possible but unsupported-feeling, and upgrades mean syncing code in the operator's clone — it fails the "bump a version input" requirement.
- **Deploy to Cloudflare button** ([docs](https://developers.cloudflare.com/workers/platform/deploy-buttons/), [blog](https://blog.cloudflare.com/deploy-workers-applications-in-seconds/), [July 2025 changelog adding vars/secrets](https://developers.cloudflare.com/changelog/post/2025-07-01-workers-deploy-button-supports-environment-variables-and-secrets/)): one click clones the upstream repo into the operator's GitHub account as an independent copy (not a fork), provisions KV/R2/D1 from wrangler config, prompts for secrets, and wires Workers Builds. It's the best zero-friction Cloudflare-native story, but the clone is a snapshot: no upstream sync mechanism, so upgrades are manual git surgery. cachet's deploy path (`alchemy`, secret bindings, env-file contract, workers-rs build) doesn't fit the button's wrangler-deploy model without re-engineering.
- No workers-ci managed-runner equivalent replaces the operator CI requirement.

## 4. Version pinning, upgrade automation, and the supply-chain trust question

- **Dependabot** has officially updated reusable-workflow refs (tags *and* SHAs) since [March 2023](https://github.blog/changelog/2023-03-13-dependabot-updates-support-reusable-workflows-for-github-actions/): `package-ecosystem: "github-actions"` bumps both `uses:` actions and `owner/repo/.github/workflows/x.yml@ref` lines ([docs](https://docs.github.com/en/code-security/how-tos/secure-your-supply-chain/secure-your-dependencies/auto-update-actions)). Known rough edge: exotic monorepo tag schemes break it ([dependabot-core#8451](https://github.com/dependabot/dependabot-core/issues/8451)); plain `repo/.github/workflows/x.yml@vX.Y.Z` is fine.
- **Renovate**'s github-actions manager updates `workflow_call` refs natively, including SHA pins with version comments (real-world: [sbaerlocher/.github](https://github.com/sbaerlocher/.github) pins by date tag, Renovate keeps it current).
- **Tag vs SHA**: GitHub docs say SHA is safest; OpenSSF Scorecard's Pinned-Dependencies check enforces SHA, and GitHub now offers an org policy to *require* full-length SHA pins. But SLSA's experience proves a reusable workflow whose internals aren't themselves fully SHA-pinned and whose release assets aren't resolvable from a bare SHA **fails outright** for SHA-pinning callers. Options: (a) ship SHA-compatible internals and let operators SHA-pin (also keep a semver tag in a trailing `# v1.4.2` comment so Dependabot/Renovate can still propose bumps), or (b) publish moving major tags (`@v1`) plus immutable patch tags and recommend patch tags. Choose deliberately and test the SHA path in cachet's own CI, since that is exactly the path security-reviewing customers will take.
- **What the upstream workflow can do with operator secrets**: everything — it runs arbitrary upstream code in a run that has been handed the operator's Cloudflare token, signing key, and OAuth secret. GitHub's documented mitigations ([secure use reference](https://docs.github.com/en/actions/reference/security/secure-use)): job-level least-privilege `permissions:`, **protected environments with required reviewers** (a deploy to `production` stalls until a human approves, which also gates environment secret access), org-level allow-lists of permitted actions/workflows, and SHA pinning. cachet must document that operators should bind `CLOUDFLARE_API_TOKEN` to a **scoped token** (Workers Scripts:Edit + KV + R2 + zone rights for exactly one zone) because Cloudflare still has no OIDC for wrangler/alchemy deploys — [workers-sdk discussion #11434](https://github.com/cloudflare/workers-sdk/discussions/11434), [wrangler-action#402](https://github.com/cloudflare/wrangler-action/issues/402), community bridge [waigel/cf-oidc-proxy](https://github.com/waigel/cf-oidc-proxy).
- **2024–2026 practitioner material** on self-host CI without forking: the reusable-workflow-with-OIDC pattern is well covered ([josh-ops](https://josh-ops.com/posts/github-actions-oidc-reusable-workflows/), [cloudchronicles env secrets guide](https://cloudchronicles.blog/blog/Passing-Environment-Secrets-and-Variables-to-Reusable-Workflows-in-GitHub-Actions/)); Cloudflare-specific "others deploy my worker" writing concentrates on the Deploy Button route above, not reusable workflows.

## 5. Recommendation for cachet

**Support two operator shapes, both released per tag:**

**Shape 1 (primary): reusable workflow `nox-systems/cachet/.github/workflows/operator-deploy.yml`.** Exact `workflow_call` surface:

```yaml
on:
  workflow_call:
    inputs:
      cachet-tag: { required: true, type: string }        # release tag to deploy
      stage:      { required: true, type: string }        # staging | production | ...
    secrets:
      CLOUDFLARE_API_TOKEN:       { required: true }
      CLOUDFLARE_ACCOUNT_ID:      { required: true }
      CACHET_SIGNING_KEY:         { required: true }
      GITHUB_OAUTH_CLIENT_SECRET: { required: true }
```

Inside: jobs set `environment: ${{ inputs.stage }}` (operator reviewer gates apply), non-secret config (`CACHET_DEPLOY_HOST`, `CACHET_DEPLOY_ORGS`, `CACHET_DEPLOY_OAUTH_CLIENT_ID`, `CACHET_DEPLOY_ADMINS`, optional overrides) read from the operator's environment `vars` context — vars are not secret-bearing, so the cross-org explicit-secrets rule doesn't touch them. The workflow downloads the **prebuilt bundle for `inputs.cachet-tag`** (no Rust toolchain on the runner) and runs the packaged alchemy program with bun.

**Shape 2 (secondary): composite action `nox-systems/cachet/deploy-action@v1`** as a thin wrapper over the same bundle+alchemy invocation, for operators who want deploy as one step inside a larger workflow and for OIDC-free simplicity of operator-owned job environments. Same secret contract via `env:`.

**What the upstream release pipeline must emit** (this is the real repo change):
1. **A prebuilt worker bundle asset per tag** (`cachet-worker-&lt;tag&gt;.tar.gz`: `worker-build --release` output + `worker-build` metadata), produced in the existing `release.yml`, so no operator machine ever needs cargo/wasm tooling — mirrors cachet-cli's cargo-dist precedent in the same repo. The integration lane should consume this asset too, so the shipped artifact is the tested artifact.
2. **A packaged deploy program per tag**: `infra/` published as a versioned tarball (or tiny npm package) containing `alchemy.run.ts`, `bun.lock`, `package.json`, and the bundle's checksum; the reusable workflow fetches both assets from the GitHub release of `inputs.cachet-tag` (public repo, no token needed) and runs `bun install --frozen-lockfile &amp;&amp; bun run deploy --stage "$STAGE"`.
3. **SHA-pinning hygiene inside the workflows themselves**: every internal `uses:` SHA-pinned (the SLSA failure mode), plus a checksum verification of the downloaded bundle.
4. **A `v1` moving tag policy** alongside immutable `v1.x.y` tags for Shape 2's action, and a documented operator quickstart: create repo, add one caller YAML, configure `staging`/`production` environments with reviewers, drop the four secrets and the `CACHET_DEPLOY_*` vars into them, run `workflow_dispatch`. Upgrades are a one-line tag bump that Dependabot or Renovate opens automatically.

Not recommended as supported paths: Workers Builds (branch-driven, no Rust image, upgrade-by-resync) and the Deploy Button (snapshot clone, no upgrade story) — at most, mention the button as an evaluation/demo on-ramp in DEPLOY.md once the bundle story exists.

# 1. Deploy to Cloudflare Workers button

Sources: https://developers.cloudflare.com/workers/platform/deploy-buttons/ , https://developers.cloudflare.com/changelog/post/2025-04-08-deploy-to-cloudflare-button/ , https://blog.cloudflare.com/deploy-workers-applications-in-seconds/ , https://github.com/cloudflare/deploy.workers.cloudflare.com (the old implementation)

**What it does today.** The button is a link of the form `https://deploy.workers.cloudflare.com/?url=&lt;public git repo URL&gt;` (subdirectories work by pointing the URL at a subdirectory path, as the cloudflare/templates repo buttons do). Clicking it walks the user through a hosted setup app that (a) clones the source repo into a new repo on the user's GitHub or GitLab account, (b) shows one setup page where the user edits repository name, Worker name, and resource names, (c) parses the repo's Wrangler configuration file, provisions every detected binding (KV namespaces, D1 databases, R2 buckets, Hyperdrive, Vectorize, Secrets Store secrets, Durable Objects, Workers AI, Queues), and writes the new resource IDs back into the clone's wrangler config, and (d) connects the clone to Workers Builds so every push to the production branch rebuilds and redeploys, and PR branches get preview URLs posted back as comments. Builds run on Cloudflare infrastructure, not GitHub Actions; the user never creates an API token by hand. Custom build/deploy commands are pre-detected from package.json scripts and editable; the default deploy command is `npx wrangler deploy`.

**Secrets and config.** Secrets are declared by the template author in a `.dev.vars.example` or `.env.example` file (dotenv format); the setup app collects values for them. Ordinary vars live in `[vars]` in the wrangler config and are copied verbatim from the template. Authors can attach per-binding explanatory text through a `cloudflare.bindings` description map in package.json (markdown inline code/bold/italics/links supported). D1 migrations must run from the user's deploy script keyed by binding name so renamed databases still migrate.

**Constraints.** Workers applications only (no Pages); repos must be public and hosted on github.com or gitlab.com (no self-hosted Git hosts, no private repos); monorepos only if the app subdirectory is fully self-contained; one button per Worker. Resource detection reads only the Wrangler config, so an alchemy stack (which declares resources in TypeScript, not wrangler.jsonc) gets no provisioning benefit. There is no mechanism for typed prompts over arbitrary config values: the flow can ask for secrets from the example env file and clone static defaults for vars, but it cannot present a form for "your GitHub orgs, your admin list, your host name". Custom domains are not provisioned or prompted for. Updating later is ordinary git pull-from-upstream plus a push.

Historical note: the previous button implementation (github.com/cloudflare/deploy.workers.cloudflare.com) was a GitHub OAuth integration that injected a GitHub Actions workflow with `cloudflare/wrangler-action` and populated repo secrets; it was replaced in April 2025 by the Workers Builds flow above.

**Fit for cachet's surface (~10 vars, 2 secrets, 1 token).** Partial. The button removes token creation and resource provisioning, but the 10 non-secret vars would ship as static clone values requiring manual edits and a second push, the custom-domain step stays manual, and the whole flow presumes a wrangler-config app, which an alchemy project is not.

# 2. create-cloudflare (C3)

Sources: https://developers.cloudflare.com/pages/get-started/c3/ , https://github.com/cloudflare/workers-sdk/pull/4754 , create-cloudflare@2.10.0 release notes, https://github.com/cloudflare/templates

Yes, third-party repos can ship C3 templates: `npm create cloudflare@latest -- my-app -- --template user/repo` (also `user/repo/subdir`, `user/repo#branch`, `user/repo#commit`, `bitbucket:`, `gitlab:`, full URLs; `--category remote-template`). Templates are cloned with degit, and the minimum required contents are a package.json, a Wrangler configuration file, and a `src/` folder containing a worker script referenced from the Wrangler config. Cloudflare's own catalog lives in github.com/cloudflare/templates and is consumed the same way (`--template cloudflare/templates/&lt;name&gt;`).

Mechanics relevant to self-hosting: after cloning, C3 installs dependencies and asks whether to deploy (`--deploy`, default true), which runs an interactive Cloudflare sign-in and deploys with wrangler; `--no-deploy`, `-y` (`--accept-defaults`), `--lang`, `--git`, `--open` control the rest. C3's prompting system covers only its built-in categories (`--category`, `--type`, `--framework`); a remote template cannot define its own prompts for config values. There is no `experimentalRemote` in the current CLI surface: the docs page documents no experimental flags, and remote-template support has been a stable `--template` option since 2.10.0. The mechanism assumes wrangler: template validation requires a Wrangler config, and the deploy step is wrangler. For an alchemy project, C3 would add nothing over `git clone`.

# 3. Other first-party machinery

**Workers Builds (GA since Developer Week 2025, April).** https://developers.cloudflare.com/workers/ci-cd/builds/ and https://developers.cloudflare.com/workers/ci-cd/builds/configuration/ . Connect a Worker to GitHub or GitLab from the dashboard (Workers &amp; Pages, Create application, Import a repository, or an existing Worker's Settings &gt; Builds). Two-step pipeline: optional build command, deploy command defaulting to `npx wrangler deploy`; preview deployments use `npx wrangler versions upload` for non-production branches. "Autoconfig" detects frameworks for repos without a wrangler config and opens a configuration PR. Limitations: the Worker's name must exactly match the `name` in the wrangler config or the build fails; one repo per Worker; no preview URLs for Workers with Containers. No beta label on these pages now.

**Versions, gradual deployments, rollbacks.** https://developers.cloudflare.com/workers/configuration/versions-and-deployments/ . A version captures bundled code, static assets, bindings, and compatibility settings (KV/R2/D1/DO contents are explicitly not versioned). `wrangler deploy` creates a version and deploys it to 100 percent in one step; `wrangler versions upload` and `wrangler versions deploy` decouple the two; `wrangler versions list` and `wrangler deployments list` show the 100 most recent of each. Rollbacks revert to a previously deployed version; gradual deployments split traffic between two versions with optional version affinity. No beta designation on the docs page.

**Secrets Store (open beta, not GA).** https://developers.cloudflare.com/secrets-store/ and https://developers.cloudflare.com/workers/wrangler/commands/secrets-store/ . Account-level secret store, one store per account, 100-secret cap during open beta. Bound to Workers through a `secrets_store_secrets` binding with `binding`, `store_id`, `secret_name` fields. CLI: `npx wrangler secrets-store secret create [STORE-ID] --name &lt;NAME&gt; --scopes workers --remote` with an interactive value prompt (the `--remote` flag is required for production operations; local mode is the default).

**workers-ci.** No wrangler feature by that name exists. The closest first-party artifact is github.com/cloudflare/ci, the `@cloudflare/ci` package, a Cloudflare-native CI engine built on Workflows and Sandbox: pipelines are TypeScript code you deploy as a Worker, requiring `nodejs_compat`. It is extremely early: 3 commits, no releases, no GA/beta label beyond its README caveats (raw logs not secret-redacted, runner commands must be idempotent under Workflow retries). Community-stage, not a product; not a deployment-UX tool for consumers.

**Templates catalog.** github.com/cloudflare/templates is the only official catalog, consumed by C3 and by deploy buttons; there is no documented third-party submission or gallery admission process.

# 5. Alchemy v2 for reusable, consumer-facing stacks

Sources: https://alchemy.run/ (homepage carries a beta badge), https://alchemy.run/llms.txt (full docs index; no template/catalog section exists), https://alchemy.run/state-store , https://alchemy.run/cli/cloudflare , https://alchemy.run/getting-started , github.com/alchemy-run/alchemy (README marks the project alpha: "Expect breaking changes")

Core verbs: `alchemy plan`, `alchemy deploy`, `alchemy destroy`, `alchemy dev`, `alchemy login` (interactive profiles saved at `~/.alchemy/profiles.json`, browser OAuth or pasted API token, managed with `alchemy login --configure` and `alchemy login --profile &lt;name&gt;`), plus `alchemy tail`, `alchemy logs`, `alchemy nuke`, and `alchemy cloudflare bootstrap / create-token / state logs`. Remote backends: `Cloudflare.state()` (a one-time-deployed state-store Worker backed by a Durable Object with embedded SQLite; its credentials are generated secrets stored in the account's Secrets Store under `StateStoreSecrets`; bootstrap happens automatically on the first `deploy`/`plan`/`dev`, or manually/idempotently via `alchemy cloudflare bootstrap`, which adopts an existing worker without `--force`; local credentials land in `~/.alchemy/&lt;profile&gt;/cloudflare-state-store.json` and with `CI=true` they are re-resolved from the Secrets Store on every run), and `postgresState({ url })` with an advisory lock per (stack, stage). Custom stores are Effect Layers; KV and R2 are not offered as built-ins.

**Reusable stacks for other people.** There is no catalog, template registry, or share mechanism anywhere in the docs index. The consumption story is structural rather than productized: a stack is plain TypeScript plus an entrypoint file (`alchemy.run.ts`), credentials come from the interactive `alchemy login` profile flow on first deploy, the first deploy itself bootstraps everything (state store, Secrets Store entries), and the `alchemy-run/alchemy@v1` action plus the GitHub provider's "Actions secrets &amp; variables" page (https://alchemy.run/github/actions-config) cover CI. This is what answers the disposable-clone question: with `Cloudflare.state()`, all state lives in the operator's Cloudflare account (state-store Worker + Secrets Store) and profile credentials live in `~/.alchemy/`, so the git clone can be deleted and re-cloned with nothing lost; `alchemy cloudflare bootstrap` is self-healing if the state store itself is damaged.
